# Three lane coding workflow

The GitHub repository created during registration is the team's shared remote. `origin` is already set to `https://github.com/BAITC-Hacks/hack-dd3ffc75-aid-soccer.git`. Work locally on a branch, push that branch, and open a pull request into `main`. Team members need write access to the organization repository to push; otherwise use a fork and open the PR from the fork.

## Freeze the starting contract

Before parallel edits, agree that `Agent.act(env) -> list[dict]` is the only submission entry point. Each campaign has a valid `target_tariff` and `channel`; optional filters are drawn from the supplied profile. Keep `agent.py` and the `campaign_agent/` package together for judging. Preserve the shared evaluation files and synthetic datasets as received.

| Lane | Owns | Concrete next improvement | Acceptance check |
|---|---|---|---|
| 1: Data and hypotheses | `campaign_agent/candidates.py`, data notes | Calibrate weak history priors and add diverse candidate search without fitting mock effects | Candidate list has valid tariffs, deterministic order, and covers several audience cells |
| 2: Exploration and integration | `campaign_agent/experiments.py`, `agent.py` | Allocate pilot sizes by value of information and observed uncertainty; maintain a safe fallback | At least one pilot, at most 20, legal sizes and no exception across ten seeds |
| 3: Portfolio and demo | `campaign_agent/planner.py`, `docs/architecture.md` | Improve budget allocation, channel choice, and evidence table for judges | At most 10 valid disjoint campaigns; contact and budget caps respected |

Only lane 2 changes `agent.py`. Each lane runs `local_eval.py` on its branch; the integrator runs the ten seed check after merging. Coordinate public function signatures in a PR description before changing them. Do not modify another lane's file merely to make a local experiment work; propose the interface change first. `submission.csv` is regenerated by the integrator after the last merge.

## Git commands

On separate laptops, each person clones the same repository and creates a different branch:

```bash
git clone https://github.com/BAITC-Hacks/hack-dd3ffc75-aid-soccer.git
cd hack-dd3ffc75-aid-soccer
git switch -c feat/data-priors       # lane 1; other lanes use feat/pilots or feat/portfolio
git add campaign_agent/candidates.py
git commit -m "Improve candidate priors"
git push -u origin feat/data-priors
```

Open a PR on GitHub from that branch into `main`; add the evaluation command and result to the PR description. Merge small PRs one at a time. Pull updated `main` before the next slice.

If three AI coding sessions run on **one computer**, isolate their working directories with Git worktrees after the starting implementation is committed to `main`:

```bash
git worktree add ../beeline-data -b feat/data-priors main
git worktree add ../beeline-pilots -b feat/pilots main
git worktree add ../beeline-portfolio -b feat/portfolio main
```

Point one GPT-6 Astra High session at each worktree. The worktrees share Git history but have separate files and branch tips. Install dependencies in each worktree's own `.venv` if needed. Do not launch three agents in the same checkout.

## Ready to paste prompts for GPT-6 Astra High

**Lane 1**

> Own only `campaign_agent/candidates.py` and data notes. Improve candidate diversity and historical weak priors using participant data only. Treat mock scores as mechanics checks, not a target to overfit. Keep `_candidates(env)` and `_prospects(candidates, limit)` compatible. Run the evaluator, explain changes and evidence in your PR.

**Lane 2**

> Own only `campaign_agent/experiments.py` and `agent.py`. Improve pilot allocation based on uncertainty and expected decision value. Use only documented `env` fields and methods; never inspect the hidden environment model. Keep the runtime deterministic and under ten minutes. Run ten seeds and report pilot count, failures, and limitations.

**Lane 3**

> Own only `campaign_agent/planner.py` and `docs/architecture.md`. Improve final disjoint campaign and channel allocation under the documented limits. Keep campaign dictionaries valid and explain any approximation. Run the evaluator and include the before and after ten seed distribution in the PR.

## Progress board

Use three GitHub issues or a small GitHub Project board: `Backlog`, `In progress`, `Review`, `Done`. Each issue should state owner, files, acceptance check, and a link to the PR. `main` is the reviewed integration branch. A short daily update can list: merged PRs, current ten seed minimum/median, submission regeneration status, and one blocking question. Do not commit API keys or local `.venv` files.
